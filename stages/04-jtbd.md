# Stage 04 — Problem / JTBD（问题定义 - Jobs To Be Done）

> **本阶段职责**：用 Jobs-To-Be-Done 框架精确定义"用户在什么场景下，雇佣这个产品来完成什么 Job"。产物是 `04-jtbd.md`。
>
> **核心理念**：哈佛 Christensen 教授的原话——"用户不是买产品，是雇佣产品来完成某个 job"。一个清晰的 JTBD 决定了 PRD 该做什么、该砍什么。

---

## 入口检查

1. Read `00-state.md` 的 `## profile` 节
2. Read `01-idea.md`（命题、目标用户）和 `03-competitors.md`（替代方案 / 用户当前怎么应付）
3. 不要求 Phase 2 必须做，但若做了请一并 Read 作为参考

## 步骤 1：开场（解释 JTBD 框架）

**编程"无" + 产品"无"**：
```
进入 Phase 4：把"用户为什么会用你的产品"想清楚。

我用一个简单的句子模板来逼你具体化：

  "当我 [在某个具体情境下]，
   我想 [完成某件事]，
   这样我就能 [得到某个最终结果]。"

例：
  "当我妈周三早上给自己量完血压、周三下午要去医院的时候，
   我想快速翻出过去一周的数据，
   这样医生不用反复问我数字、我也不用慌着回想。"

这比"我想要个血压记录功能"具体 100 倍。
```

**PM / 工程师**：
```
进入 Phase 4：JTBD 定义。

用 Christensen 的标准 job statement：
  When [situation],
  I want to [motivation],
  So I can [expected outcome].

输出 1 个 main job + 2-3 个 related jobs。
```

---

## 步骤 2：苏格拉底式追问（2 轮）

### 第 1 轮：触发场景（Situation）

```
问题 1：用户**最可能**第一次拿出你的产品是什么瞬间？
描述时间 + 地点 + 当时手里在做什么 + TA 的情绪状态。

例（不好）：「想看血压的时候」
例（好）：「妈妈周三上午 8:00 量完血压，看到收缩压 145 比平时高 10，紧张。
         手机已经打开微信准备问儿子。」

问题 2：触发场景一周大概会发生几次？
- 几乎每天
- 每周 1-3 次
- 每月几次
- 触发不规律 / 看情况
```

### 第 2 轮：动机和期望结果

```
问题 1：用户在那个瞬间真正想完成的 job 是什么？
注意：不是"打开你的 app"——是 app 帮他/她完成的事。

例：「快速判断这次血压是不是值得担心」
例：「不用回想数字就能告诉医生过去一周的趋势」

问题 2：完成这个 job 后，用户希望得到什么结果？
（不是产品功能，是用户拿到的"价值"）

例：「不用焦虑，知道下一步该不该看医生」
例：「在医生面前不显得'什么都不知道'」
```

## 步骤 3：探索 related jobs

主动提出可能的相关 jobs 让用户确认：

```
基于你的描述，我猜你的产品可能还会被"雇佣"来完成这些次要 jobs：

- {{related job 1，如"给在外地的子女自动同步数据，让他们安心"}}
- {{related job 2，如"打印一份月度报告带去医院"}}
- {{related job 3，如"用药提醒"}}

哪些是你觉得**也很重要**的？哪些是"以后可能会做"？哪些"完全不在范围内"？

（这一步直接影响 Phase 5 PRD 的 MVP 范围）
```

## 步骤 6：Exit gate

- [x] `04-jtbd.md` 写完

- [x] 触发场景有具体时间、地点、情绪、手里在做什么
- [x] Related Jobs 至少 1 条且明确标了 MVP/V2/永不

满足后勾选 Phase 4、追加决策快照、等用户 `/dream-weaving next`。

---

## 反例

- ❌ Job statement 写成功能描述（"我想点击按钮看图表"）
- ❌ situation 写成"想用的时候"（这不是 situation）
- ❌ 跳过 Anti-Jobs（这是 PRD 砍范围的关键）
- ❌ Related jobs 不分优先级，全部 ✅
- ❌ 不引用 Phase 3 的竞品失败点（脱节）
