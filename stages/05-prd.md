# Stage 05 — PRD / MVP Scope（产品需求文档 + 最小可行范围）

> **本阶段职责**：把 Phase 1-4 的认知凝结成"V1 要做什么、不做什么"的具体清单。产物是 `05-prd.md`。
>
> **核心理念**：MVP 不是"砍配置"的产品，是"完整解决一个 job、其他全部砍掉"的产品。要敢于做减法。

---

## 入口检查

1. Read `00-state.md` 的 `## profile` 节
2. Read `01-idea.md`（命题）+ `04-jtbd.md`（Main Job + Anti-Jobs）
3. Read `02-research.md`（如有，调整建议）+ `03-competitors.md`（差异化 wedge）
4. 缺失任何前置 → 提示用户回去补

---

## 步骤 1：开场（强调"减法")

**编程"无" + 产品"无"**：
```
进入 Phase 5：把 V1 范围钉死。

我会逼你做"减法决策"——什么放进 V1，什么放到 V2，什么永远不做。

V1（也叫 MVP）只解决你 Phase 4 写的 Main Job：
  "{{Main Job 一句话}}"

只要这个 Job 解决了，哪怕产品丑、慢、缺功能，都算 V1 成功。
所有"如果再加 X 就更好了"的想法都先放到 V2/V3。
```

**PM**：
```
进入 Phase 5：PRD + MVP scope。

我会按 P0/P1/P2 强行排序所有候选功能，并把 P2 砍到 V2。
注意：MVP 不是"减少功能配置"，是"完整解决 Main Job 而其他一律不做"。
```

## 步骤 2：发散候选功能列表

输出现有信息引出的候选功能候选清单（让用户对照）：

```
基于 Phase 1-4，我推断你**可能想做**的所有功能（无序）：

A. {{从 Main Job 直接派生的功能 1}}
B. {{从 Main Job 直接派生的功能 2}}
C. {{从 Related Job 1 派生的功能}}
D. {{从竞品对标补的"必须有"功能}}
E. {{从差异化 wedge 派生的"独特"功能}}
F. {{常见但你可能没想到的功能：登录 / 数据备份 / 设置 / ...}}

请补充我漏掉的（如有）。
```

等用户补充后，进入步骤 3。

---

## 步骤 3：AskUserQuestion 强制排序

```
对每个候选功能，把它放到下面 4 档之一：

P0 — V1 必须做（不做就不算解决 Main Job）
P1 — V1 想做（做了体验好很多，但没有也能用）
P2 — V2 候选（先验证 V1，再考虑）
P3 — 永不做（产品 anti-jobs 或永远不会回报投入）

我会逐条问你。
```

然后**逐个**用 AskUserQuestion 问每个候选功能（每次最多 4 个，分批问）。

**反规则**：
- 如果 P0 数量 > 5，必须把溢出的功能"降级"到 P1 — 因为 V1 做超过 5 个 P0 功能极少能成功
- 如果一个功能用户标 P0 但和 Anti-Jobs 冲突，主动指出冲突让用户决定

---

## 步骤 4：苏格拉底式追问 V1 边界

针对最终的 P0 列表追问：

```
问题 1：如果只能保留 1 个 P0 功能，你保留哪个？
（你的回答会成为 "single most important workflow"，是 V1 的核心）

问题 2：如果发布前两周内必须再砍掉 1 个 P0，你砍哪个？为什么砍它？

问题 3：V1 上线后 1 个月内，看哪个数字判断成功？
- 用户数（如 100 个真实用户）
- 留存率（如 30% 周留存）
- 频次（如平均每用户每周打开 3 次）
- 反馈质量（如 5 个用户主动说"再不用就难受"）
```

---

## 反例

- ❌ P0 功能 > 5（已知失败模式）
- ❌ "数据导出"、"通知系统"放进 P0（几乎都可以延后）
- ❌ 验收标准写成"功能正常工作"
- ❌ 成功指标写"很多用户"、"有人付费"
- ❌ 跳过永不做这一节
- ❌ Story 没有边界条件
